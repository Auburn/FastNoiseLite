# Conformance suite

Every FastNoiseLite port should produce the same numbers as the C++ reference (`Cpp/FastNoiseLite.h`).
This suite checks that. Each port has a small driver that evaluates noise and domain warp for a shared
set of configurations and points, and `run.py` compares the output with the C++ output.

```sh
python3 conformance/run.py            # every port that has <Port>/conformance/build.sh
python3 conformance/run.py Go Rust    # just these ports
```

Requirements: Python 3, a C++ compiler (for the reference), and the port's own toolchain. Results go to
`conformance/out/<Port>/` (git-ignored), the reference output to `conformance/out/Cpp/`; `log.txt` has
the build output and any errors the drivers print.

## How it works

1. **Reference.** `run.py` builds `Cpp/conformance/driver.cpp` (float and double coordinates) and runs it
   on every vector set. The output hashes must match `reference.sha256`, so an unintended change to the
   C++ output is caught too.
2. **Ports.** For each port, `run.py` runs `<Port>/conformance/build.sh`, which builds the port's driver
   and lists its variants (precisions or build modes). `run.py` then runs each variant's driver on each
   vector set.
3. **Compare.** Every output value is compared with the float and the double reference, and the closer
   one counts. Each value is judged on its own scale (a warped `x` near 0 is not excused by a large `y`):

   | Tier | Meaning |
   |---|---|
   | exact | equal up to printing precision |
   | tol | within float rounding (noise: 2e-4) |
   | small | the size of difference float vs double arithmetic alone produces |
   | MISMATCH | larger than that, or non-finite where C++ is finite. Almost always a logic difference |

   An output's **bad count** is MISMATCH values + missing values + unparsable or duplicate lines (+ the
   small values at ordinary points, if there are more than 40, because then the difference is
   systematic, not rounding). A port passes when every output has a bad count of 0 and no driver
   exited with an error.

Vector sets (generated by `gen_vectors.py`):

- `vectors/main`: 180 configurations (every noise type × fractal type × 3D rotation, every cellular
  distance/return combination, every warp type × warp fractal, edge parameters, seeds at
  `INT_MAX`/`INT_MIN`) at 36 2D and 36 3D points.
- `vectors/edge`: cellular, Perlin, Value and ValueCubic at frequency 1, at negative half-integers
  (rounding ties) and at lattice indices up to 8,000,000 (32-bit hash multiplies that lose bits when
  done in floating point). All coordinates are exact in float32, so every correct port matches closely.

## Adding a language

A new port needs two files in `<Port>/conformance/`. The drivers in `C/`, `JavaScript/` and `Java/`
are good starting points; most drivers are 70–130 lines.

### 1. The driver

`driver VECTORS_DIR` reads three files from `VECTORS_DIR` and prints results to stdout. It may take
extra arguments of your choosing before `VECTORS_DIR`, such as the precision to test (the Go and Zig
drivers do this).

- `points2d.txt`: one point per line, `x y`.
- `points3d.txt`: one point per line, `x y z`.
- `configs.txt`: one configuration per line, 15 whitespace-separated fields:

  `seed frequency noiseType rotationType3D fractalType octaves lacunarity gain weightedStrength pingPongStrength cellularDistanceFunction cellularReturnType cellularJitter domainWarpType domainWarpAmp`

  Enum fields are the ordinals of the C++ enums:

  | Field | Values |
  |---|---|
  | noiseType | 0 OpenSimplex2, 1 OpenSimplex2S, 2 Cellular, 3 Perlin, 4 ValueCubic, 5 Value |
  | rotationType3D | 0 None, 1 ImproveXYPlanes, 2 ImproveXZPlanes |
  | fractalType | 0 None, 1 FBm, 2 Ridged, 3 PingPong, 4 DomainWarpProgressive, 5 DomainWarpIndependent |
  | cellularDistanceFunction | 0 Euclidean, 1 EuclideanSq, 2 Manhattan, 3 Hybrid |
  | cellularReturnType | 0 CellValue, 1 Distance, 2 Distance2, 3 Distance2Add, 4 Distance2Sub, 5 Distance2Mul, 6 Distance2Div |
  | domainWarpType | 0 OpenSimplex2, 1 OpenSimplex2Reduced, 2 BasicGrid |

  If your port's enum values differ, map by name.

The driver evaluates two kinds of instance:

1. **Default instance.** A default-constructed instance with no setters called, printed as config `-1`.
2. **Config instances.** For each line of `configs.txt`, a fresh instance, printed as config 0, 1, 2… in
   file order. Set it up in this order: seed, frequency, noise type, rotation type, fractal type, octaves,
   lacunarity, gain, weighted strength, ping-pong strength, cellular distance function, cellular return
   type, cellular jitter, domain warp type, domain warp amp. If your port uses a state struct instead of
   setters, assign the fields.

For every instance `c`, the driver prints, in this order:

```
N2 c i <GetNoise(x, y)>                       for each 2D point i
N3 c i <GetNoise(x, y, z)>                    for each 3D point i
W2 c i <x> <y>                                for each 2D point, after DomainWarp(x, y)
W3 c i <x> <y> <z>                            for each 3D point, after DomainWarp(x, y, z)
```

Print at least 9 significant digits. If a call throws and your language can catch it, skip that line
and carry on; skipped lines count as missing. Leave out calls your port can't make at all yet, with a
comment saying why. Exit with status 0 when done.

### 2. `build.sh`

`run.py` runs `build.sh` in an empty output directory, `conformance/out/<Port>/`, which is also where
the drivers run. `build.sh` builds the driver there and writes `variants.txt`, one line per variant:

```
float ./driver_float
double ./driver_double
```

- The first word names the variant: a precision or build mode, for example `float`, `double`,
  `f32-debug` or `js`. Test every precision your port offers.
- The rest is the command that runs the driver, in shell-style quoting; `run.py` appends `VECTORS_DIR`.
  Paths are relative to the output directory. Refer to files in the repository through the script's own
  location, `$(dirname "$0")`.
- Write build products only in the output directory, never inside the repository.
- If a precision is selected by editing the source (a `typedef` or `using` line), make the edited copy
  with `conformance/replace.sh SRC DEST FROM TO`, as the C, C#, HLSL and Java scripts do. It fails when
  `FROM` isn't found, so a changed switch can't quietly turn the double variant into a second float one.
- Exit non-zero if the build fails. If there is nothing to build, check that the toolchain is installed
  (the JavaScript and PowerShell scripts print its version).

### 3. Run it

```sh
python3 conformance/run.py MyLang
```

Fix mismatches until the port passes. For each failing output, the report names the configs and points
that mismatch and shows the expected values; `--show N` shows up to N of them (default 10). The outputs
are in `conformance/out/<Port>/<set>.<variant>.txt`, next to the reference's in `conformance/out/Cpp/`.

### 4. CI

Add the port to the `matrix` in `.github/workflows/conformance.yml`, plus a step that installs its
toolchain if the `ubuntu-24.04` runner image doesn't already have it. The maintainer can do this when
merging. Each port is its own CI job, so a failing port shows up as its own red check; the run's
summary page has a table of bad counts per port, vector set and variant.

## Changing the reference

If a change to `Cpp/FastNoiseLite.h` or to the vectors is meant to change the output, run
`python3 conformance/run.py Cpp --update-reference`. Commit the new `reference.sha256`; ports then show
up as regressions until they are updated to match.

## Not covered

- **GML.** There is no headless GameMaker runtime.
- **Coordinates beyond the 32-bit integer range** (`|coord × frequency| ≥ 2^31`). Converting them to a
  lattice index is undefined behaviour in C++, so there is no reference to compare against.
